## 第 4 条机制拆解（为何"queued 但已收到"是自洽的）

`status --conversations` 的末条状态 = **本机发送账本（send-log）中该对话对时间最新一条**——只记录"我发出的消息的结局"，对端回信不产生本机账目。时序还原：

1. 主会话 → worker4 末条消息：对端忙 → `queued` = **已确认交入 worker4 的 codex 队列**（daemon ≥0.160 队列投递；消费时机对 crosschat 不可见——零轮询是 B8 的设计特性，否则每条消息都需轮询对端）
2. worker4 轮末消费该消息 → 发出收官回信 → 主会话收到

两件事完全自洽：**`queued` 在账本里是终态（已交单），回信到来即是消费完成的天然回执**。缺口仅在展示层没把这句话讲出来，读的人误读为"悬而未决"。

## 落地修复

- `status --conversations` 人类视图：末条为 `queued` 时行尾自动加注"（已交对端队列待消费——对方回信即证明已处理）"（JSON 输出不动）
- README 发送状态说明补 `queued` 语义与"账本为本机发送视角"注记

## 教训入档

- 状态语义凡有"不可见的后半程"（队列消费/看门狗重投），**展示层必须自带解释**，不能依赖读者推断——本轮 `queued` 如此，`parked` 已有队列深度输出无此问题
