# C14 显式工具类型收敛稿

状态：2026-10-28用户在全量任务重排后明确“开始下一个任务”，按当前尚未完成的C14恢复本稿整改；逐入口无法可靠确认的例外方案仍须另行过目拍板，不自动视为获批。此前逐项同意及覆盖关系见[批准历史](c14-user-command-review.md)。本稿是实施合同，不是验收记录；讨论前技术验证不代表新规则已实现，不开始C08等下一项。

## 用户命令及操作影响

| 操作 | 收敛行为 | 用户影响 |
| --- | --- | --- |
| 主动发送 | `crosschat send --to <名称或完整原生ID> --tool <收件类型>` | 所有send必填tool，只有一个候选也不省略；同类型重名用完整ID |
| 按信封回信 | `crosschat send --conversation cN --tool <收件类型>` | 程序生成完整hint；agent照用，不猜类型；cN是本机通信关系短柄 |
| TCP发送 | `crosschat send --via tcp:<星>:<机器>:<名称或完整ID> --tool <收件类型>` | 保留机器段，tool独立于地址；不恢复已退役的机器级ambient投递 |
| SSH发送 | 既有SSH路由透传收件tool，由远端解析 | 不宣称有TCP同款能力握手；不丢类型回退 |
| 原工具前缀 | 取消`<工具>/<会话>`作为用户选型语法，不做兼容分支 | 原生名称/ID中的斜杠作为原值；内部ref/origin编码与显示标签不因此删除 |
| TUI现有y | 改为复制选中目标的完整发送命令 | 包含完整ID、tool、路由和正文占位；只复制，不发送；保留完整ID/结构化SessionRef复制 |

```powershell
crosschat send --to 测试会话 --tool codex-desktop --body "正文"
crosschat send --via tcp:main:电脑A:测试会话 --tool codex-desktop --body "正文"
crosschat send --conversation c3 --tool codex-cli --body "回复正文"
```

引号是shell引用规则，不是地址协议；目标有空格或特殊字符时才需适当引用。`--to`与`--conversation`继续互斥；前者找目标且可复用已有通信关系，后者续接关系并发送给另一参与方，两者都不自动附带聊天历史。结构化SessionRef不是cN。

现类型登记为`claude`、`codex-cli`、`codex-desktop`、`opencode`、`dsh`、`dsh-desktop`；不因本稿新增类型改名或别名政策。OpenCode CLI/Desktop连接同一HTTP服务时共用`opencode`类型，不按窗口虚构两个端点。Harness正式Desktop仍须独立验收。

## 路由、引用和成员

1. 已确认收件端点写入通信引用；Desktop不可用就报告不可用，不转投CLI。`--tool`与固定类型冲突拒绝；有意选择另一端点用`--to`及相应tool。
2. 同原生ID的不同实际端点分别通信记录、cN和轮次，分别保持当前星成员资格。删除只影响该端点在当前星的接收路径，不删原生聊天、不终止工具、不影响其他端点或星。
3. 既有未知类型引用按本次明确tool核实补齐，保留原cN、nonce和连续轮次；较旧未知状态不能覆盖已确定类型。不因取消旧地址语法而删除全部ref/历史。
4. 带类型的TCP投递遇到缺少类型能力的broker/node，拒绝并说明哪个crosschat需升级；不得丢类型兼容投递。
5. 信封独立展示已知`from-tool`，未知如实标为待核实；回复照hint，不根据展示字段拼装路由。`from-addr`不再承载工具前缀。

## 自动识别优先，人工确认跨会话复用

send的tool始终表示收件端；自身类型由Provider原生接入自动识别，程序无法分辨时才询问用户。用户确认记录为人工分类依据，不冒充原生已直接给出类型。

| 层次 | 处理内容 | 复用与变化 |
| --- | --- | --- |
| 来源分类 | 当前机器/用户下，可核实原生入口或Host域及其工具类型 | 同来源的多个会话共享一次确认；不按工具家族全局保存CLI/Desktop选择 |
| 运行核验 | 实例、进程出生信息、实际连接/owner代次、版本及profile/home | 重启、升级或断连后重核；运行证据失效不等于必须再问用户 |
| 本次调用 | 当前完整原生ID及调用到实际来源的关联 | 每次重取和核验；会话切换不自动导致类型重问 |

来源的稳定范围必须由Adapter给出证据。若只能关联当前实例，则仅在该实例内共享；不能仅凭相同安装路径、目录、ID、活root或某个活owner扩大范围。CLI/Desktop实际入口、不同机器/用户、无法证实等价的profile/home分别处理。

首次并发时，程序按来源维护一个共享待确认项，只有一个会话展示询问；其他会话看到已有待确认并复用答案，不各发一问。未答不代表同意；询问会话退出时其他活会话接续原待确认项。展示权有界且可释放，不把已退出进程当永久owner，不要求用户找回旧会话。

已接入的独立确认入口：

```powershell
crosschat identity confirm --tool codex-desktop --context "程序生成的确认引用"
```

此处tool表示要确认的自身类型；它不属于send，不改变send参数含义。`crosschat identity` 返回结构化探测结果，只有 `shouldAsk:true` 才能询问用户；agent得到回答后执行程序生成的确认操作，用户不手填context。通用确认状态机已实施隔离验证，但真实未知入口的人工策略尚未逐项获批，当前均不创建询问。可复用来源关联和原生询问owner存活核验须同时具备，不能只打开一个允许人工确认的开关。

确认前重新核实来源及当前待确认状态。仅运行换代而来源仍相同时，先自动重核，核验通过继续复用。来源暂不可达时可保留已答选择为待重核，恢复后自动核验，不让用户重复回答；不能提前宣称识别成功。旧回答不可改绑到新来源，不因迟到探测覆盖新结论。

程序能识别、已有有效确认、新建同源会话、正常重启升级且自动重核通过，都不询问。只有自动识别及可复用确认均无法解决、实际需要确认新来源或处理类型冲突时才询问；解释具体变化，不能每个新会话都问。

若某入口连当前调用到实例的关联都无法取得，就记录适配能力缺口，继续核实原生接口；不用全局“未知Codex”缓存或反复提问伪称完成。此时不承诺任意入口都能永久只问一次。

这些规则不新增鉴权/认证体系、常驻daemon、模型key或`--from-tool`，不自动安装/升级工具。缓存和待确认状态复用既有状态根原则，具体并发存储在实施时按原子条件写入处理，不改变通信/成员键。

## 无法可靠确认的入口先交用户拍板

用户补充明确要求：“哪些不能通过会话确认的，需要我过目，拍板”。凡不能通过原生会话/程序可靠确认自身类型的入口，或者人工确认后仍无法持续核验、跨会话复用的情形，均须按具体入口整理证据和方案给用户过目；Q19对兜底方向的同意不代替这些具体能力缺口及处理方案的批准。

先区分四种状态：已有可靠自动识别依据、已有路线但待接线/验证、经验证无法自动识别但可核实人工确认的范围、连人工确认后的持续关联也无法核实。未接线或未验收不等于原生不支持；不能先宣布某工具无法识别，或自行确定用户接受哪种限制。

每项交付用户决策的清单包括：工具及CLI/Desktop/Web入口、版本与操作系统、可读取的原生依据、实际缺失字段/关联及验证证据、能否人工确认及其可复用范围、对首次发送/回信/多会话/重启的影响、推荐方案与替代方案、待用户决定的具体事项。在拍板前，不擅自把某入口降为逐会话询问、缩小支持范围、禁用入口或更改既有命令/安装要求；其他已确定路径的独立研究及验证可继续。

当前需验证的重点如下；这些不是已经证实“无法确认”的工具名单：

| 入口 | 当前已知与待验证内容 | 提交用户拍板的条件 |
| --- | --- | --- |
| Codex CLI/Desktop | 原生会话/逐调用字段已有；本次调用与实际CLI/Desktop入口的持续关联仍需接线验证 | 验证后仍不能自动区分，或只能在有限实例范围人工确认时，明确范围及影响后提交 |
| OpenCode CLI/Desktop共享服务 | 本批类型统一为opencode，不需要询问CLI/Desktop；多个服务实例的精确来源关联待补 | 多服务来源无法可靠关联，或需额外Hook/插件与安装配置变化时，提交具体方案 |
| Harness npm/Web | 公开shellEnv子生命周期已接线；正式0.2.1-rc.2 npm/Web两轮通过逐调用实例/profile/原生ID关联，见[本轮记录](c14-explicit-tool-validation-20261028.md)；Host重启、多Host及平台增量仍待验收 | 后续验证仍存在识别或复用限制，或需改变插件安装/配置要求时提交 |
| Harness正式Desktop | 类型/profile路线存在，但正式Desktop原生shell及多会话来源关联须独立验证 | 不用Web结果代替；正式入口验证后仍有限制时单独提交 |

当前研究尚未得出某个完整入口“经上述接线及验证后仍必然无法确认”的最终结论。完整事实和Claude原生识别依据见[研究统计](../research/c14-caller-identity-research-20261028.md)。

这是开发阶段按入口能力做的方案决策，不是每个运行会话再审批一次。用户批准同一适用范围的策略后由程序复用，新会话、正常重启升级且自动重核通过时不重复请求拍板；实际能力或范围发生变化、自动恢复仍失败而需更改策略时，再提交具体变化。

## 必须保留的发送与教学规则

- Q8保留：caller原生身份匹配、既有引用的收件目标明确时，来源类型未知或只读来源探测暂不可用仍允许正常回信；不额外要求发送方证明窗口owner。不允许用用户分类补造缺失或冲突的原生ID。
- 普通human终端既有单向发送许可不顺带禁用；不能因为等待自身类型确认就新增统一禁发规则。收件tool仍必填。
- skill解释主动发送/按hint回信、自身识别/收件选择，以及只用原生身份、不猜造变量。hint和TUI模板由程序带齐收件tool。
- 用户明确委托转达继续按既有规则加`--delivery steer`，自主协调默认queue，多行或敏感shell字符用stdin。命令模板替换正文即可，用户不负责转义细节。
- 写入/发送结果不明不自动重发；有界只读探测不重启、resume或改写原生工具。
