## Q18研究交付与下一决策

只读研究已完成，见[总报告](../research/c14-caller-identity-research-20261028.md)。已找到各工具可利用的原生接缝，当前Windows Desktop还实测了可读进程链及两次独立调用的稳定session/变化tool-call指纹；不是多turn/三平台或Hook/owner关联验收。Harness有公开每次shell执行环境贡献机制，可研究把既有bridge实例与本次调用精确关联。Codex的原生调用ID/Hook/执行实例关联仍需接线验证。不能把研究方案记为已实现。

根据用户的兜底要求，下一项用户面提议为独立的自身类型确认入口，例如 `crosschat identity confirm --tool <自身类型> --context <程序生成的本次确认引用>`。该命令仅为提议，尚未批准或实现；不属于send的收件类型参数，不新增 `--from-tool`。程序生成确认引用以固定待确认的会话/实例上下文，确认时重新核对，避免迟到回答绑定到已切换的会话；用户确认记录来源，后续每次send重新核验同一上下文，不依赖模型记忆。无法关联实例时必须如实说明能力缺口，不能把一次确认当独立原生证明。整体方案仍待最后共同理解确认，不开始开发。

用户追问“Q19是什么意思”，没有批准新增命令。需先以实际流程解释：仅在当前调用无法自动分类时，由agent询问用户当前入口，随后通过程序生成的确认操作把回答保存到当时的会话/实例；后续由程序重核，核验通过不重问。`--context`只关联待确认上下文，不要求用户生成/填写；该流程本身不能补造缺失的原生实例关联，自动识别仍优先。Q19保持待确认，不实施。

## Grilling 第十二轮：Q19条件批准

用户在解释后明确：“这个兜底同意，但是必须是在无法分辨的情况下”。据此批准自动识别失败时才询问用户自身类型，并由程序保存、后续复核；能自动识别时不得询问。独立确认操作只负责自身分类，send的 `--tool` 始终是收件类型，不新增 `--from-tool`。拟议的 `identity confirm` 具体入口与整合方案一同做最后确认，尚未实施。

前轮以“本会话＋实例”描述一次确认的范围过窄。它适合每次调用核验，不能成为每个新会话都重新问用户的理由。

## Grilling 第十三轮：多会话复用及询问去重

用户指出：“这个无法识别的工具，多个会话可能都会重复询问用户，这个就狠不好体验”。将避免逐会话重复询问列为C14的明确需求；以下是对该需求的具体收敛方案，待整体确认：

- **来源分类共享**：Adapter能核实来自同一工具入口/Host域时，一次用户类型确认供其多个会话复用。稳定来源关联不足时只能在可核实实例范围内共享；不按裸工具名、安装路径、会话ID或活owner猜测合并CLI/Desktop。
- **调用分别核验**：每次重新读取完整原生ID并关联实际来源/当前运行代次。类型共享不合并通信对、轮次或成员资格，不令新会话自动入星。
- **首次并发去重**：同来源只有一个共享待确认项，只有一个会话负责展示询问，其余复用待确认结果，不各问一次。未回答不是同意，不反复提示；首问会话退出时其他活会话可接续原待确认项，不永久等待原会话。
- **重启升级先复核**：进程/owner/连接或版本变化使旧运行证据失效；先自动重探测，仍能关联同一来源且分类相容就沿用，不无条件重问。来源不可达时保留已给答案为待重核，恢复后自动核验；旧回答不能改绑到不同来源。
- **真实缺口不以提问掩盖**：连本次调用到实例的关系都无法核实时，记录Provider入口能力缺口，不承诺任意会话都能只问一次，也不创建全局“未知工具”缓存或逐会话询问循环。Q8正常回信与human既有单向发送许可继续保留。

这些是来源分类的复用规则，不新增鉴权系统、常驻daemon或用户手填标识。完整命令、变更影响、接线与验收见[收敛稿](c14-explicit-tool-design-20261028.md)；原CI任务不删不改为完成。

## 讨论前的命令解释（历史，已由Q17覆盖）

“类型＋名称/完整 ID”中的加号表示组合条件，不输入命令。当前待确认写法是在原有 `--to` 上增加可选的 `--tool`：

```powershell
crosschat send --to "测试会话" --body "你好"
crosschat send --tool codex-desktop --to "测试会话" --body "你好"
```

第二条将收件范围限制到 Codex Desktop；同一类型内还有重名时，再使用完整原生 ID。`--tool` 只限定收件端，不证明发信 shell 的归属，也不选择某个桌面窗口。上述第一条省略类型的示例仅记录讨论前行为；Q17已决定所有send显式提供收件类型，第一条将报参数缺失。`--to`、`--conversation`分工和互斥关系保留。

OpenCode CLI/Desktop 共用 HTTP 服务时仍为 `opencode`，不能据此区分当前窗口。类型登记、命令写法和其余边界见[当前实现说明](../tool-types.md)，该说明在批准前不作为最终用户合同。

## 讨论前实现快照（批准结论以上文为准）

| 项目 | 当前工作区实现及对用户的影响 |
| --- | --- |
| 可选参数 | 新增 `--tool <类型>`；与 `--to` 或回信使用，限定收件端。用户尚未单独批准这个参数形式。 |
| 地址形式 | 新增 `codex-cli/`、`codex-desktop/`、`dsh-host/`、`dsh-desktop/` 等严格端点前缀，TUI复制地址及部分回信地址随之改变；旧 `codex/`、`dsh/` 仅为家族限定。 |
| 无类型完整 ID | 当前发现候选中同一 Codex 完整 ID 同时出现于 CLI/Desktop 时，由可能选首项改为报 `NAME_COLLISION`，需明确收件类型。类型拆分也可能增加同名候选。普通未限定发送仍保留既有20条发现上限，不承诺全量查出所有重复。 |
| 旧无类型对话引用 | 旧 `--conversation` 的收件端无类型且存在多个端点时，新增 `TARGET_TYPE_REQUIRED`；核实收件端后补 `--tool`。 |
| 自动回信 | 原生 shell 只提供会话 ID，续接带类型对话时新增完整候选核验；歧义、未知/矛盾类型、缺失或来源不可读会报 `CALLER_IDENTITY_UNRESOLVED`，可能使原自动回信失败。补收件端 `--tool` 不能解决发信端身份；当前代码指引核实后用 `--to` 发新消息，不能视作完全等价的回信。此项需单独确认。 |
| 投递回落 | 有明确端点时不跨类型回落，Desktop owner 不在线不会转发 CLI；从普通 `--to` 的发现行解析出类型后，也携带该约束。 |
| TUI | 同 Provider、同原生 ID 的 CLI/Desktop 可分为两行；类型显示、筛选、复制地址与刷新选择按端点区分。 |
| 跨机 | 带类型的 TCP 路由/引用要求相应 broker、node 支持 `endpoint-types-v1`，不支持时报 `BAD_PROTO`；SSH透传类型并由远端解析，不宣称有同一套能力握手。混用旧端可能使原可用操作失败。 |
| 对话及记录 | 新引用、队列及关联按端点区分，旧无类型记录保持未知；用户可能看到同一原生 ID 的两类端点分别出现。 |
