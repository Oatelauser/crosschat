# C14 短信封恢复：歧义短柄的事实、候选与批准边界

2026-10-29（UTC+8）。C14-W07 研究单 + W07-R1 返修。起始 `58508d6a78865e884df684092da9979351683f68`（首轮），返修基线 `572280dd69e391c5d850401adb9a7a59208d24d8`，branch `codex/core-refactor-pre-tui`。本单不改产品、不碰用户状态、不试发；不追认真实历史 c14 由哪次竞争产生。**首轮“别名式恢复 + 不改 LRU8 + 旧号不动”可闭环的结论已被 root 审计推翻，本稿撤回该结论。**

## 一、结论先行

1. 用户看到的“hint 又变成长 mc2”已复现：历史 c14 在两个分片里各绑一个不同 nonce 时，`handleForRef` 返回 `undefined`，`composeEnvelope` 回退完整 ref（E1）。
2. “直接补分配一个新号”不是修复：真实 API `claimHandle(file, ref, 15)` 会顶掉本分片同 nonce 的旧 c14，另一方的 c14 随即从歧义变成唯一——旧信封里的 `c14` 静默改投另一段对话（E3）。
3. “追加别名、保留旧号”同样不闭环：**满 8 槽时追加会立即淘汰首键**，若首键正是撞号一侧，恢复当刻就把旧号判给对方（E6 / root 复放）；靠淘汰别的键腾槽，被淘汰的可能是另一组撞号的旧柄，同样替那一组选赢家。**这不是“以后普通淘汰/清理”的风险，而是恢复动作本身的矛盾。**首轮第四节对“零合同变化闭环”的表述撤回。
4. 剩下的候选都有明确条件，且都未获批准：无空槽时不得追加（只能返回 undefined）；有空槽才追加的方案仍改变别名槽位/刷新语义，且不提供“旧歧义持续拒绝”的保证；机器级冲突账本是另一项需要用户决定的持久化提案。**W08 未获授权，不能因本单声称可以推进。**
5. “旧柄永不误指”需要新持久信息：LRU 单边淘汰、`clean` 删分片、号可被 max+1 重用，三条各自都能让旧号改投，今天已如此。任何提案都必须写明写序与失败次序，并明确保证范围只是“已成功登记的冲突号”。
6. 写失败现状：本机 Windows 的只读目标场景下，分配是单次写 + 写后校验，失败后分片字节不变、无幽灵柄、无 tmp（E5）。它**只**证明这一条失败路径，不代表所有写失败或崩溃都字节不变。

## 二、事实（源码 + 隔离实测）

实验脚本 `docs/development/evidence/c14-worker-20261029/W07-probe.mjs`；首轮结果 `W07-result.json`（SHA256 `e256133b…ee302`，本单未改），返修结果 `W07-R1-result.json`（新增 E6）。只调用构建后 `dist/conversations.js|ref.js|envelope.js`，状态根为本单独占 `node_modules/.cache/w07-probe-*`。撞号初态（API 已不能再产生）用直接写分片表达，其余每一步都走真实导出函数。

### 2.1 为什么没有柄

`handleForRefLocked`（`src/conversations.ts:602-611`）只要求**任一**同 pair 同 nonce 的现存柄安全即可复用（`mine.find(...)`）；`resolvesToNonce`（`:613-619`）以“解析成功且 nonce 一致”为安全，`resolveHandle`（`:649-662`）遇跨 nonce 撞号直接抛 `INVALID_CONVERSATION_REF`，异常被吞后返回 false。于是当 `mine` 里没有任何安全柄时返回 `undefined`。信封侧 `conversationArg = handle ?? ref`（`src/envelope.ts:87`）回退完整 ref（`:98-100`）。E1 实测：`handleForRef → null`，hint 为 `--conversation mc2_…`。

三类“多条记录”要分清，本单只处理第一类：

- **历史歧义**：跨分片两个不同 nonce 共用同一号（用户这次遇到的），API 已不会再产生，但旧状态还在。
- **类型细化副本**：同 nonce 的 untyped/typed 两份，`resolveRefinementCopies`（`:665-677`）会合成一个可解析结果，属已验收容错。
- **新并发撞号**：W04 已修，本单不重开、不当作新成果。

### 2.2 为什么不能“直接 claim 一个新号”

`claimHandleLocked`（`:632-642`）→ `attachHandle`（`:552-564`）→ `refreshHandles(existing, ref, newHandle)`（`:519-545`）。带 `newHandle` 时，循环里同 nonce 的旧条目走 `continue` 且不写回 `next`（注释：“superseded by newHandle — dropped”）。这是“同 nonce 换号”的去重语义，用在撞号恢复上就变成：**删的是本对话的旧号，留下的另一份旧号独占该数字**。

E3 实测（两分片各持 `c14`，nonce 不同）：`claimHandle(file, refA, 15)` 返回 `c15`，本分片 `{c14}→{c15}`，会话行 `ref/updatedAt` 未变，对方分片字节未变；`resolveHandle('c14')` 由抛“撞号”变为返回**对方** ref（`isForeign:true`），`c15` 唯一指向本对话。

任何“改写其中一侧”的做法（包括把对方的 c14 迁到新号、或通过淘汰别的键保住我们的 c14）都只是换一边选赢家。

### 2.3 双柄为什么不自动稳

`refreshHandles` 无 `newHandle` 的刷新腿对每个同 nonce 条目只记 `touched = handle`（后者覆盖前者）并 `continue`，循环结束只把**最后一个**写回。E4 实测：`{c14,c15}` 同 nonce，`recordConversation(下一轮)` 后只剩 `{c15: 新 ref}`，`c14` 又解析到对方。所以“只加柄不改刷新腿”的翻转只是推迟到投递成功后一瞬。

要让别名存活，刷新腿必须改成“每个同 nonce 别名都就地换成本轮 ref”——这改变当前同 nonce 去重与 LRU 触碰/槽位语义（原来同 nonce 多柄是临时态，改后成为持久态），不能称为 LRU 语义完全不变。

### 2.4 满槽反例（本单新增 E6）

用真实 API 在 A 分片按 `c14..c21` 顺序分配 8 个不同 nonce 的柄，B 分片另持一个不同 nonce 的 `c14`（历史撞号，`resolveHandle('c14')` 此时抛撞号）；再给 A 追加第九个不同 nonce 的柄 `c22`：

- A 分片变为 `c15..c22`，最老的 `c14` 被 `HANDLE_MAX=8` 的首键淘汰；
- `resolveHandle('c14')` 立即返回 **B** 的 ref；
- B 分片字节未变。

E6 证明的是**现有 LRU 淘汰规则**，不是尚未实现的别名分配器的运行结果；把“追加别名”接到这条规则上，就是恢复当刻的满槽矛盾。若为腾槽改淘汰次序（例如跳过撞号键），被淘汰的仍是某个旧键，而旧键里可能包含**另一组**撞号的柄——同样替那组选赢家；“只保护当前对话的旧号”不构成安全论证。

### 2.5 写失败、并发与残留

- `attachHandle` 单次 `savePair`（tmp + rename）后回读校验，校验不过返回 false，`claimHandle` 抛 `CONVERSATION_STATE_WRITE_FAILED`；发送在投递前失败，不发消息。
- E5（**仅本机 Windows 只读目标**）：分片设为只读后 `claimHandle` 抛写失败，分片字节与初态逐字节相同（旧 c14 保留、仍撞号），目录无 `.tmp`。这只覆盖该失败路径。
- 并发由 `withConversationLock`（`:576-580`）串行化；`claimHandleLocked` 的 CAS 在“候选号已属他处”时改用 `max+2` 再写一次。
- **CAS 首次候选本身也可能与外来绑定重复**。第一次写会先落地；重试会顶替本次刚写的号。残留期间该号在我们分片与外来分片各一份，解析侧按撞号拒绝——“它属于我们”不是安全论证；它只是不构成幽灵柄。写序、失败次序与残留清理必须在任何实施单里写定，不能默认残留无害。

### 2.6 四个公开写 API、只读入口与维护删除

`claimHandle` 在 `src/` 内无生产调用方（仅测试）；生产只经 `handleForRef` 进入分配。**公开会话写 API 是四个**：

| 写 API | 位置 | 与恢复的关系 |
| --- | --- | --- |
| `handleForRef` | `conversations.ts:596-611`；`send/index.ts:473-475`、`federation.ts:363-364`、`serve/via-tcp.ts:536-537` | 分配/复用柄；无安全柄时返回 undefined —— 恢复点 |
| `claimHandle` | `conversations.ts:626-642` | 分配原语（仅测试直接调用） |
| `recordConversation` | `conversations.ts:424-456` | 刷新腿；失败吞掉不影响已投递 |
| `continueFromRef` → `reconcileRefinement` | `:259-364` | 迁移柄：目标号属他人则跳过（不选赢家），迁移后按 `HANDLE_MAX` 修剪（`:337`） |

**只读**：`continueConversation`（`:222-241`）、`resolveHandle`（`:649-677`）、`latestKnownConversationRef`、`machineNameOfPair`、`loadAllPairs`、`queries/files.ts` 展示。恢复方案不得需要改它们的语义。

**维护删除**：`clean/force-clean` 在 `application/maintenance/operations.ts:62-72` 无锁删 `conversations/*.json`，属既有“无传输时执行”合同；任何“冲突号不因清理变成赢家”的保证都必须说明清理对它的影响。

## 四、备选方案的条件与批准边界（均未批准，不启动 W08）

### 4.1 机器级短柄账本（root 建议，需用户决定）

在分片目录之外保存“已登记冲突号 + 递增编号”，纳入现有同一把锁；先原子登记冲突与预留新号，再写新柄；解析优先拒绝登记号；普通分片仍 8 槽；`clean/force-clean` 保留账本，只有卸载或清空整个状态才重置。

必须写明的边界：

- 代价：新增持久信息、清理后的保留规则、可能跳号（号只增不回收）。
- 账本无法安全读取/保存时：不发新短柄，完整 ref 保持原投递途径；**不得为可选 hint 引入无必要的发送失败**。
- 崩溃或第二次写失败可能留下跳号或拒绝记录；**不可倒退编号，也不可选旧号赢家**。
- 保证范围：**已成功登记的冲突号**不因分片淘汰/清理而变成赢家；不能追认已丢失的历史绑定，也不证明任意历史柄永久安全。
- 实施前须把全部写路径（2.6 四个 API）与失败次序写成确切合同并逐条测。

### 4.2 有空槽才追加别名（较弱，需用户确认影响）

- 条件：仅在目标分片有空槽时追加新号并保留旧号；满 8 槽一律返回 `undefined`（完整 ref），**不得为腾槽删除任何旧键**。
- 仍需改动：刷新腿保留全部同 nonce 别名（见 2.3）；CAS 重试只顶替本次刚写的号。
- 明确影响：别名占用 LRU 槽；同 nonce 多柄由临时态变持久态，触碰/去重语义改变；后续普通淘汰/`clean` 仍可能让旧冲突只剩一侧，旧号仍会改投。
- 因此它不是“旧歧义持续拒绝”的修复，只是“有空槽时能重新给出安全短柄”。必须明确接受上述影响才可实施。

### 4.3 维持现状（完整 ref 回退）

不补分配、不改存储：消息照发，旧号歧义继续显式拒绝，无新保证。可作为“不支付任何持久化成本”的基线。

### 4.4 无论选哪项，实施前必须写定的断言

1. 满槽 + 撞号首键：恢复不得删除任何旧键，结果为 `undefined`（4.2）或先登记再预留（4.1）；旧号仍拒绝解析。
2. 有空槽时恢复：新号唯一指向本对话；旧号仍在且仍撞号；对方分片字节不变；会话行/轮次/类型/nonce/路由不变。
3. 刷新后：别名都指向本轮 ref（若采用 4.2）；`resolveHandle(旧号)` 的拒绝语义不变。
4. LRU8：别名计入槽位；普通对话（单柄）槽位与今天一致；淘汰次序有断言。
5. 并发：同对话并发恢复得同一个新号；不同撞号对话并发得不同新号；CAS 重试不产生孤立别名。
6. 写失败：恢复失败回落 `undefined`（长 ref 照发），分片字节不变、无 tmp、无幽灵柄；普通分配失败仍抛 `CONVERSATION_STATE_WRITE_FAILED`（`conversation-state-concurrency.test.ts:315` 锚点）。
7. 端到端：完整 ref 经撞号只投递一次、hint 安全、投递后记账失败仍只投递一次。
8. 细化：撞号对话带别名做 untyped→typed 迁移，不选赢家，修剪行为有断言。
9. 若采用 4.1：登记/预留/写柄的失败次序、崩溃残留、`clean` 后的账本保留各自有断言。
