# 长对话的上下文策略

label: wayfinder:grilling
status: closed
blocked-by: （无）
claimed-by: 主会话（2026-10-01，B4 前定案）

## Question

两个 agent 互聊轮数上去后，各自会话的上下文必然膨胀（Q6 的附带推论，上个 session 已暴露此担忧）。定一个一期能落地的最小策略：

- 外部转录：消息历史落盘，会话内只保留最近 N 轮 + 按需读档？
- 摘要轮换：每 K 轮由一方产出对话摘要替换原文？
- 消息预算：单条消息长度上限 + 总轮数上限 + 终止条件？
- 或者明确决定一期不处理、只记录风险（也是合法决策）

权衡维度：实现成本 vs 上下文占用 vs 对话连贯性。

## Resolution

一期上下文策略 = **预算 + 计数提示**（用户 2026-10-01 拍板），重型机制不上：

1. 单条 body 上限 **16KiB**（常量借 embassy `ledger.ts`）
2. 自包含会话引用内嵌**轮次计数**（引用本来就存在，零成本）；信封显示"第 N 轮"
3. skill 行为准则：N 接近题词预算 → 主动总结收尾；**预算数字归题词**（终止归题词层，003 已定）
4. **超限语义**（用户追问补定）：一切硬限（16KiB / 速率 30 条/60s/对端点）= `send` 同步显式报错（`MESSAGE_TOO_LARGE` / `RATE_LIMITED`）交发送方 agent 自纠；**绝不静默截断、绝不静默丢弃、绝不自动重试**。长内容的标准自纠路径 = **落盘后发路径引用**（同机共享文件系统是天然泄压阀，接收方按需读——顺带缓解上下文膨胀）
5. 摘要轮换 / 外部转录档案 → 二期雾区，等一期真实使用数据

理由：消息本身占上下文有限（20 轮 ≈ 几十 KB），真正的爆炸源是 agent 反复读大文件——一期管这个反而干扰干活；便宜护栏先行。
